# 질의서 및 회신 관리

`data/baseline.json`의 `미확정사항` 12건은 아래 두 문서로 시행한다.
각 항목의 `질의번호`가 문서의 질의 문항과 1:1로 대응한다.

| 문서 | 수신 | 문항 | 성격 |
|---|---|---|---|
| `01_아산시_확인요청_시행문.docx` | 아산시장 (도시계획과 스마트도시팀) | 1-1 ~ 1-5 | 아산시 자체 확인사항 |
| `02_국토교통부_질의안.docx` | 국토교통부장관 (경유: 한국스마트도시협회) | 2-1 ~ 2-7 | 아산시 명의로 시행 요청 |

## 왜 두 건으로 나누는가

㈜제일엔지니어링은 **간접보조사업자**이므로 중앙관서에 직접 질의할 수 없다.
국토교통부 소관 사항은 보조사업자인 아산시 명의로 시행되어야 하며,
문서 02는 아산시가 그대로 쓸 수 있도록 작성한 **초안**이다.

## 회신 반영 절차

회신이 오면 `data/baseline.json`을 갱신한다. 문서 수정이 아니라 **원장 갱신**이다.

```jsonc
{
  "항목": "사업기간 종료일 및 준공 기준시점(협약 제14조②)",
  "확인처": "국토교통부·아산시",
  "중요도": "최상",
  "질의번호": "2-1",
  "문서번호": "도시활력지원과-1234",
  "질의일": "2026-09-01",
  "회신일": "2026-09-20",
  "상태": "회신완료"
}
```

동시에 회신 내용을 실제 값에 반영하고 `confirmed: true`로 전환한다.

```bash
git commit -m "data(baseline): 준공 기준시점 확정 (국토부 회신 도시활력지원과-1234, 2026-09-20)"
```

커밋 메시지의 공문번호가 감사 시 근거가 된다. 반드시 기재한다.

`미확정사항`이 모두 `회신완료`가 되고 `confirmed`가 모두 `true`가 되면
**R-01이 해소되어 정산보고서 산출이 열린다.**

## 작성 원칙

각 질의는 다음 4단으로 구성했다.

- **관련 규정** — 조문 특정. 근거 없는 질의는 회신이 늦다
- **질의 배경** — 왜 불분명한지. 담당자가 판단할 재료를 준다
- **질의 사항** — 묻는 것을 번호로 분리. 통으로 물으면 일부만 답이 온다
- **검토 의견** — **우리 해석을 먼저 제시한다.** 백지 질의보다 "이렇게 보고 있는데 맞는가"가
  회신이 빠르고, 회신이 늦어도 우리 해석대로 진행한 근거가 남는다
